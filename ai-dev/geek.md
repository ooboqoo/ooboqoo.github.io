## 普通程序员如何迈进 AI 时代

### AI 时代，程序员依然有用

虽然 AI 时代是构建在许多顶尖的 AI 算法基础上的，但整个社会要真正进入 AI 时代，算法和模型必须和我们的现实生活结合起来。这里有大量工程性的工作需要完成，而这恰恰是普通程序员的强项。

当真正接触了 AI 应用开发，你就会发现，我们完全可以把别人构建好的模型当做基础设施来用，站在这个角度上看，*这同我们使用 API 构建应用没有本质区别*。不过，与我们简单地调用 API 传入参数不同，基于大模型的 AI 应用开发有不同的编程模式。



编程范式的转变：程序的执行规则不再是完全的硬编码


### 基于大模型的 AI 应用开发

*基于大模型的 AI 应用开发需要我们有不同的编程模式*。传统的应用开发是程序员把执行规则一条条写进代码里，而大模型时代，其中部分工作会交给大模型去做。哪些事情可以交给大模型去做，以及如何指导大模型完成工作，则是普通程序员需要补充的知识。


## 大模型基础

* 了解大模型的基本知识。大模型是支撑我们应用开发的基础，需要了解但不需要深入
* 从普通用户的角度学习如何编写 **提示词**
* 从事 AI 应用开发需要进一步挖掘大模型能力，即学习 **提示工程**

### 技术视角的大模型

大模型的工作模式很简单：一次添加一个 token

引入随机性：有了随机性，对于同样的提示词，我们每次得到的内容可能会不同。**温度 Temperature** 用于表示随机性强弱。

从字符串到向量：AI算法无法直接处理文本、图像、视频内容，必须先*把各种信息转换成向量*。

字符串转成向量会经历两个步骤
* 第一步叫 One-Hot 编码，将离散的分类值转换为二进制向量（示例：颜色的RGB编码）
* 第二步则是把编码的结果进行压缩，以得到最终的 Embedding

获取 Embedding 常用的方法有两种：降维和把 Embedding 训练成神经网络。降维的技术有很多，如主成分分析（Principal component analysis）。但在大模型中，通常使用把 Embedding 训练成神经网络的方法，也就是把我们前一步得到的向量送给一个神经网络，得到最终的压缩过的向量。

在大型模型中，Embedding 是一种将高维数据（如文本、图像、视频等）转换为低维向量表示的技术。这种技术在自然语言处理（NLP）、计算机视觉等领域有着广泛的应用。Embedding 的核心思想是将离散数据映射到连续的向量空间，使得相似的数据点在向量空间中的距离较近，而不相似的数据点则距离较远。

### 提示词（用户使用）

> 提示词 = 定义角色 + 背景信息 + 任务目标 + 输出要求

网友的观点：提示词 = 你是谁 + 我是谁 + 我要干什么 + 按我的要求给我干活

与 GPT 的连续对话可以让我们更好地理解问题，更加清晰地表达自己的需求。

### 提示工程（AI应用开发）

提示工程指南 https://www.promptingguide.ai/zh

在开发者眼中，我们需要的是*大模型处理复杂任务场景的能力*，比如，现在很多 Agent 背后的技术就是让大模型推断出下一步的行为，这是利用大模型的推理能力，而这依赖于提示词的编写。

网友观点：
* AI 应用工程师  = system提示词工程师
* 这么说 RAG 也是一种提示工程

几个基本的提示技术：
* 零样本提示：用于通用的任务
* 少样本提示：用于特定的简单任务
* 思维链提示：引入推理过程，可以与零样本提示和少样本提示结合 （现在 Reasoner 模型都内置了推理能力）
	* 少样本提示，提供推理过程
	* 零样本提示：Let's think step by step
* ReAct 框架（Reason + Act）：将大模型推理和一些行动能力结合起来，超越大模型自身的限制
	* 在这个例子里，大模型为了完成一个大目标，需要不断地做一些任务。每个任务都会经历思考（Thought）、行动（Action）、观察（Observation）三个阶段。
	* LangChain 示例 https://smith.langchain.com/hub/hwchase17/react

返回参数

前面几个参数都非常好理解，接下来的 choices 才是我们应答的重点，这是大模型给我们回复的真正内容。choices 本身是一个对象列表，其中的每个对象就是大模型生成文本的一部分。我们来具体看一下：index，索引。这就是一个顺序编号，如果文本被切分了，通过索引就可以将内容重新排列，生成正确的顺序。不过，如果对于标准的 HTTP 应答，切片的必要性不大，往往只有一块。`finish_reason`，停止生成 token 的原因。文本不会无限生成，总会停下来。到了停止点或遇到停止序列，原因就是 `stop`，到了一定的长度，原因就是 `length`，生成了工具调用就是 `tool_calls`。message，回复的消息。在这个例子中，包含了两个字段：角色（role）和内容（content）。这个部分与请求中的消息是一样的，最核心的字段就是内容，角色部分已经解释过了（可以回看上一讲的核心参数部分）。除了常规的回复内容之外，如果回复内容是一个工具调用，也是通过 message 里返回的，我们再来看一个例子：

```json
{
```

## 模型能力

### 开源模型

基于大模型的应用开发，一个关键问题是成本，一方面，如果所有请求都必须通过闭源模型，则成本会居高不下，另一方面，很多开源大模型能力越来越强，某些模型的表现不亚于闭源模型，比如 Meta 出品的 Llama 系列，很多情况下，我们完全可以使用开源模型进行替代。

### 模型微调

同 RAG 类似，微调是另外一种帮助大模型扩展知识面的技术，不同的是，RAG 是把知识补充到提示词里，而微调则是在模型上动了手脚。RAG 和微调各有千秋，RAG 成本更低，微调效果更好（如果做得好的话），AI 应用常常根据自己的需要选择其中一个。不过，某些项目会选择将二者都包含其中。

### 案例一：知识库效果不佳

* 团队采用 RAG 的方式打造了一个知识库
* 现象是：效果不佳，显得很不智能

技术团队解决问题的思路
* 如何做数据清洗
* 如何做好文档分块
* 如何找一个靠谱的 Embedding 模型
* 如何选一个好的检索方式
* 如何通过重写，让用户提示词更适合在系统中做查询

真实困境：没有好知识可以放到知识库里
* 企业有的是文档，而不是经过整理的知识
* 企业希望知识库能够有优秀员工的经验

“非技术”问题：隐性知识 vs. 显性知识
* 想入库的是*隐性知识*（员工经验），但系统需要*显性知识*（结构化文档）
* 本质：这是一个知识萃取（Knowledge Extraction）问题，是经典的知识管理范畴
* 解决方案：转向业务部门，通过访谈、工作坊等方式进行知识萃取

“非技术”问题：文档 vs. 知识库
* 把文档直接丢给系统，效果欠佳
* 本质：文档不是一个有效的知识源，不能与 RAG 系统有效配合
* 解决方案：*把文档进行预处理，拆分成有效的问答对*
* 技术方案：借助大模型进行预处理，可能的话，进行人工审核


### 案例二：全盘 AI 化

* 现象：纠结于产品应该推到重来，还是修修补补。
* 常见诱惑：把所有系统都变成“聊天界面”才叫AI化。

AI 产品化的两条路径
* AI 原生（AI Native）：从头按照 AI 的方式设计一个产品
* AI 增强（AI Augmented）：在现有的产品上，增加 AI 能力

企业系统演化策略
* 两条路径分析
	* AI 原生：性感，但高风险，适合新产品
	* AI 增强：务实，低风险，适合现有系统
* 核心原则：如果没坏，就不要去修它。稳健高于技术性感
* 对大多数企业而言，渐进增强是更优策略

小提示：后端服务的 AI 改造
* AI 改造，需要有一个服务路由，将老功能转到老服务上，新功能转到新服务上
* 老功能可以封装一个工具或 MCP，供新的 Agent 使用
* 这是遗留系统改造的思路，用在 AI 改造上

### 案例三：Agent 系统太复杂

* 现象：Agent 效果有限，尤其是引入多 Agent 设计混乱，职责不清，工作流臃肿。
* 技术焦虑：是不是要用最前沿的框架？更进一步，哪个 Agent 框架是最好的呢？

Agent 系统设计本质上还是一个软件设计
* 软件设计要遵循软件设计原则
* KISS 原则：优先用单 Agent，非必要不多用
* 单一职责原则
	* 每个 Agent 都承担单一职责
	* 多 Agent 系统需要先进行 Agent 的职责分配
* Agent 就是软件模块，工作流就是业务流程的代码体现

AI 是新的，问题是老的
* 统一接口：组合模式 Composite Pattern
* 职责分配：模块化设计 Modular Design
* 渐进增强：遗留系统改造策略 Legacy System Modernization
* 结论：强大的软件工程基本功，是开发现代 AI 系统的基石

Agent 系统设计：选择构建 Agent 的契机
* 传统的自动化，适用于确定性强，能够基于规则执行的工作流
* 面对复杂、模糊、需要判断的工作流时，传统规则引擎和确定性方法力不从心
* 构建 Agent，应优先考虑以前一直拒绝自动化的工作流程，尤其是传统方法会遇到摩擦的地方
	* 复杂决策：涉及对上下文敏感的细微决策的工作流，例如客户服务工作流中的退款审批
	* 难以维护的规则：因大量复杂规则集而变得臃肿的系统，导致更新成本高昂或容易出错，例如执行供应商安全审查
	* 严重依赖非结构化数据：设计解释自然语言、从文档中提取含义或与用户进行对话交互的场景，例如处理家庭保险索赔

Agent 系统设计：技术方案
* 熟悉常见的 Agent 模式：单 Agent；多 Agent
* 通用建议：尽量使用单 Agent，最大化单 Agent 能力
* 多 Agent 系统，先考虑职责分配，再选用适当的模式
